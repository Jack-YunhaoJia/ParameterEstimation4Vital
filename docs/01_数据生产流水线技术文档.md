# 当前 preset-first 数据生产流水线技术文档

## 1. 文档目的

本文档描述当前仓库里已经落地的 `preset-first` 数据生产链路，也就是：

`真实 .vital 预设 -> 路由掩码增强 -> 多条件渲染 -> 音频预处理 -> embedding -> HDF5`

本文档只描述当前实现，不描述尚未落地的理想设计。对于旧版 45 维随机采样生产链，请参考 `scripts/run_production.py` 及相关旧模块。

## 3. 当前生产逻辑

### 3.1 端到端流程

当前 `PresetDatasetProducer.produce()` 的执行顺序为：

1. 扫描 preset 目录，过滤无法 JSON 解析的 `.vital`
2. 解析所有有效 preset，得到 `(base_preset_id, VitalPreset)`
3. 解析并统计 wavetable 信息
4. 可选执行 `factory_only_mode` 过滤
5. 根据 `run_mode` 选择本轮处理的 base preset 子集
6. 基于当前子集提取 `CorpusSchema`
7. 以 `base_preset_id` 为粒度做 `train / val / test` 划分
8. 加载或初始化 `checkpoint.json`
9. 对每个未完成的 base preset：
   - 构建路由图
   - 生成变体
   - 写出变异 `.vital`
   - 在多个 MIDI 条件下渲染
   - 对音频做预处理
   - 提取 embedding
   - 编码参数向量并写入 split buffer
10. 定期把 split buffer flush 到 `shards/<split>/shard_xxxx.npz`
11. 全部完成后把 shards 合并为最终 `preset_corpus_dataset.h5`
12. 输出 `production_summary.json`

### 3.2 当前渲染条件

当前 `preset-first` 主线通过 `RendererBackend -> MultiConditionRenderer` 走固定的 6 个 MIDI 条件：

| 标签 | note | velocity | 当前时长 |
|------|------|----------|---------|
| `C3_v80` | 48 | 80 | 2.0s |
| `C3_v120` | 48 | 120 | 2.0s |
| `C4_v80` | 60 | 80 | 2.0s |
| `C4_v120` | 60 | 120 | 2.0s |
| `C5_v80` | 72 | 80 | 2.0s |
| `C5_v120` | 72 | 120 | 2.0s |

当前这条主线默认还没有接入自适应时长计算器，所以这里的 `midi_duration` 目前是固定值 `2.0`。

### 3.3 run mode

当前 producer 支持三种模式：

| 模式 | 作用 |
|------|------|
| `pilot` | 小样本验证，默认用于当前 9 个 preset |
| `canary` | 中等规模验证 |
| `full` | 全量语料生产 |

当前 `scripts/run_pilot.py` 固定使用：

- `run_mode="pilot"`
- `pilot_max_base_presets=9`
- `pilot_max_variants_per_base=4`
- `resume=True`，除非显式传 `--no-resume`

### 3.4 split 逻辑

当前数据集不是按样本随机切分，而是按 `base_preset_id` 先分组再切分：

1. 对 base preset ID 去重
2. 用固定 seed 打乱
3. 按 `0.8 / 0.1 / 0.1` 分到 `train / val / test`
4. 同一 `base_preset_id` 的所有 variants 和渲染条件都落到同一个 split

这保证了：

- 同源变体不会跨 split 泄漏
- 评估更接近“见过相似音色族、但没见过这个 base preset 本体”的场景

## 4. 当前数据结构

### 4.1 `ScanResult`

扫描阶段返回：

- `preset_paths`
- `total_found`
- `failed_paths`
- `failed_errors`

### 4.2 `IntrospectionReport`

保真审计阶段为每个 preset 统计：

- `total_settings_count`
- `applied_count`
- `skipped_count`
- `unsupported_count`
- `active_modulation_count`
- `wavetable_count`

当前实现里：

- `applied` 的判定依赖 `audio_renderer._vital_name_to_pedalboard()`
- `skipped` 目前基本未展开，主要还是 `applied / unsupported`

### 4.3 `CorpusSchema`

`CorpusSchema` 是当前 `preset-first` 数据集的核心结构，决定了 `param_values` 的列顺序和解码方法。它包含：

- `param_names`
- `param_types`
- `param_value_encoding`
- `default_values`
- `corpus_min`
- `corpus_max`
- `presence_ratio`
- `category_values`

其中最关键的是：

- `param_values` 统一为单个 `(N, D) float32` 矩阵
- `continuous / binary` 直接写数值
- `categorical` 先映射成 `category_id`，再写成 `float32`

### 4.4 `RouteGraph` 与 `MaskedVariant`

当前增强链路的核心对象为：

- `RouteEdge`
- `RouteGraph`
- `RouteMask`
- `MaskMetadata`
- `MaskedVariant`

增强逻辑：

- `variant_0` 永远保留原始 preset
- `K <= 8` 时做有界穷举
- `K > 8` 时做随机采样
- 所有有效 mask 都要求至少保留一条 `source -> output` 可达路径

## 5. 参数编码逻辑

### 5.1 为什么是单个 `float32 param_values`

当前训练侧、DataLoader 和模型接口都天然消费 `(embeddings, params)` 这种稠密张量形式，因此 producer 当前选择：

- 所有可训练字段统一进入 `param_values`
- categorical 字段用 `category_id` 编码
- 缺失字段由默认值填充
- `present_mask` 额外记录“原始 preset 是否真的含有该字段”

### 5.2 `present_mask` 的含义

对于样本中第 `j` 个字段：

- `present_mask[j] == 1`：该字段确实存在于原始 `preset.settings`
- `present_mask[j] == 0`：该字段在原始 preset 中不存在，`param_values[j]` 是用 `default_values` 填充的

### 5.3 当前 modulation / wavetable 字段状态

当前 schema 会预留：

- `modulation_k_*`
- `osc_i_wavetable_id`
- `osc_i_wavetable_source_type`

但当前 sample-level 编码主要仍基于 `preset.settings`。因此在现实现状下：

- 这些结构化扩展字段已经在 schema 层有位点
- 但如果没有先把相关信息显式注入 `preset.settings`，落盘时通常会表现为默认值 + `present_mask=0`

这意味着当前 HDF5 结构已经为更完整的 modulation / wavetable 学习预留了接口，但 sample-level 语义还没有完全展开。

## 6. 输出目录与中间产物

以 `experiments/pilot_run/` 为例，当前 producer 典型输出为：

```text
experiments/pilot_run/
├── audio/                    # 渲染出的 WAV
├── variants/                 # 变异后的 .vital
├── shards/
│   ├── train/
│   ├── val/
│   └── test/
├── checkpoint.json           # resume 状态
├── corpus_schema.json        # 本轮 schema
├── preset_corpus_dataset.h5  # 最终数据集
└── production_summary.json   # 生产摘要
```

其中：

- `shards/<split>/shard_XXXX.npz` 是中间落盘格式
- `checkpoint.json` 用于 resume
- `preset_corpus_dataset.h5` 是最终训练数据入口
- `production_summary.json` 是外部摘要，不在 HDF5 metadata 中

## 7. checkpoint / resume 逻辑

当前 resume 机制的核心是：

- `checkpoint.json`
- `shards/`

checkpoint 记录：

- `run_mode`
- `selected_base_preset_ids`
- `completed_base_preset_ids`
- `split_assignment`
- `schema_path`
- `shard_manifest_path`
- `summary_so_far`
- `last_completed_stage`

resume 的行为是：

1. 如果 `resume=True` 且存在 `checkpoint.json`，则加载已有 checkpoint
2. 跳过 `completed_base_preset_ids` 中已完成的 base preset
3. 继续生产剩余 preset
4. 最终重新做 HDF5 finalize

## 9. 当前实现边界与注意事项

### 9.1 Fidelity Spike 的现实含义

当前 `PresetRenderAudit` 会把“存在 active modulations / wavetables，但当前 backend 不会真正注入这些结构”视为 gap。因此在复杂 preset 语料上，`Fidelity Spike` 很可能给出：

- `backend_replacement_recommended`

也就是说，`Fidelity Spike` 现在不是“形式性通过项”，而是用来诚实暴露当前渲染路径保真不足的门控。

### 9.2 `route_edge_schema_json` 仍是占位

当前 HDF5 metadata 中虽然有 `route_edge_schema_json`，但内容还是 placeholder，不应视作完整的路由 schema 规范来源。

### 9.3 embedding 失败回退

当前如果 `EmbeddingExtractor` 初始化失败，producer 会写入 1024 维零向量占位，以保证流程联调能走通。正式生产前必须确保：

- MuQ 模型正常可用
- 生成的数据中 embedding 不是占位零向量

### 9.4 旧链路仍然存在

仓库中仍保留：

- `scripts/run_production.py`
- `src/parallel_producer.py`
- `src/training_data.py`

它们对应的是旧版 `parameter-first` 随机采样生产逻辑。当前文档不以它们为主，但它们仍可作为历史数据和 baseline 的参考。
